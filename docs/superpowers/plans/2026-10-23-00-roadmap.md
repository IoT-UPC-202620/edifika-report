1. **Un carril, un repo.** Ningún agente edita archivos de otro carril. Excepción: la Task 4 del Plan 1 y la Task 5 del Plan 2 implementan los dos extremos del sync, y ambos siguen los contratos §2 al pie de la letra.

3. **TDD por tarea:** primero el test que falla, luego la implementación, luego la suite en verde y luego el commit. Ningún commit con tests en rojo.
4. **Sin push, sin repos remotos y sin tocar `edifika-report/wokwi/firmware/**`** (obsoleto). El firmware que se modifica es solo el del repo `esp32`, y solo en el carril G. **No se toca `esp32/src/ModestIoT/`.**

## Gitflow y commits (obligatorio en todos los carriles)

El patrón es el que ya usa `Edifika-Microservice-IoT-Gateway`. Los repos que no usan gitflow (los nuevos, el ApiGateway y la plataforma) lo adoptan igual.

**Ramas**
- **`main`:** solo recibe merges de `release/*` y `hotfix/*`. Nadie commitea directo.
- **`develop`:** rama de integración. Si no existe, se crea desde `main` (`git checkout -b develop main`). En los repos nuevos: `git init -b main`, un commit inicial `chore: initial commit` con `.gitignore` y `README.md`, y luego `git checkout -b develop`.
- **Feature por tarea**, nacida de `develop`: `feature/<HITO>-<slug-en-ingles>`. Ejemplos: `feature/H1-amqp-publisher`, `feature/H2-door-reservations`, `feature/H5-iot-routes`.
- **Cierre de cada tarea**, con la tarea en verde: `git checkout develop && git merge --no-ff feature/<…>`. El mensaje es el que genera git por defecto: `Merge branch 'feature/<…>' into develop`. Después se borra la rama local.
- **Release:** cuando el hito del carril queda cerrado, se crea `release/<x.y.z>` desde `develop`, con un commit `chore(release): prepare <x.y.z>` que actualiza CHANGELOG y versión. Luego se hace merge `--no-ff` a `main` y a `develop`, y se agrega el tag `v<x.y.z>`.
  - Versiones: Edge Gateway `0.2.0`; Access Management `0.1.0`; Telemetry `0.1.0`; Platform `0.1.0`.
  - ApiGateway: **sin release**. Su feature queda mergeada en `develop` para que el equipo decida.
- **Sin push** a ningún remoto.

**Commits: Conventional Commits, en inglés, específicos**
- Formato: `<type>(<scope>): <imperative description in English>` y, al final, entre paréntesis, el hito y las historias que cubre: `(H1)`, `(H2, US45)`.
- Tipos: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `build`, `ci`, `perf`.
- Scope: el módulo tocado, como `amqp`, `sync`, `access`, `devices`, `reservations`, `telemetry`, `routes` o `contracts`.
- Un commit = un cambio con sentido propio. Nada de `feat: changes` ni `wip`. Una tarea normalmente tiene un commit, o dos si el test y la implementación conviene separarlos (`test(...)` + `feat(...)`).
- Cuerpo opcional, en inglés, explicando el porqué cuando no sea obvio.
- Los mensajes de commit que aparecen en los planes son la guía: se respetan el tipo, el scope y el sentido, y se les agrega el sufijo del hito.
